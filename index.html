Tema 6

Docker en Azure: registro, máquina virtual y Compose

Llevamos a Azure lo que hicimos en local: empaquetamos una API Spring Boot (pokeAPI) y su front en Astro en imágenes de Docker, las subimos a un Azure Container Registry y, en una máquina virtual, las descargamos y las arrancamos juntas con docker-compose, conectadas a una base de datos MySQL de Azure.

1Qué vamos a montar

En el Tema 5 todo ocurría en tu ordenador: construías la imagen y la ejecutabas ahí mismo. Para desplegar hay que llevar la aplicación a otra máquina, y la forma habitual con Docker es pasar por un registro de imágenes: tú subes la imagen una vez y cualquier servidor puede descargarla.

Cuando alguien abre la página, la petición llega al puerto 80 de la máquina virtual, la recibe el contenedor del front, que pide los datos al contenedor de la API, y esta los consulta en la base de datos de Azure.

Por qué el front llama a la API con http://backend:8085 y no con la IP pública El front usa renderizado en servidor (SSR): quien llama a la API es el servidor de Node que corre dentro del contenedor del front, no el navegador. Y dentro de la red que crea Compose, cada servicio se encuentra por su nombre (backend es el nombre del servicio en el docker-compose.yml). Así la API no necesita publicar ningún puerto: solo la ve el front.

2Los recursos de Azure y los conceptos nuevos

Cada pieza de Azure es un recurso. Para esta sesión usamos tres, más un par de configuraciones de red:

RecursoPara qué lo usamos
Grupo de recursosCarpeta lógica que agrupa todos los recursos del proyecto. Conviene crear todo en el mismo grupo: así se ve junto y se borra de una vez
Container Registry (ACR)Almacén privado de imágenes de Docker. Su dirección es nombre.azurecr.io
Máquina virtualEl servidor Linux (Ubuntu) donde corre Docker con nuestros dos contenedores
Azure Database for MySQLBase de datos MySQL gestionada por Azure. No la ponemos en un contenedor: es un servicio aparte
Reglas de puerto de entradaEl "cortafuegos" de la máquina virtual: qué puertos se pueden alcanzar desde internet (22 para SSH, 80 para la web)
Reglas de firewall del MySQLLista de IP que pueden conectarse a la base de datos. Hay que añadir la IP pública de la máquina virtual

Y tres ideas nuevas de Docker:

ConceptoQué es
RegistroServicio donde se guardan las imágenes. Docker Hub es el público; ACR es el privado de Azure
Nombre completo de imagenregistro/nombre:etiqueta, por ejemplo miregistro.azurecr.io/pokeapi-back:1.0. El registro por delante es lo que le dice a Docker a dónde subirla
Etiqueta (tag)La versión de la imagen (1.0, 1.1…). Cada versión nueva se sube con una etiqueta nueva

3El proyecto: pokeAPI y su front

Son dos aplicaciones que ya conoces de las asignaturas de Spring: una API de Pokémon con entrenadores, fichas de estadísticas y habilidades, y un front que las muestra.

API (pokeAPI)Front (pokeAPI-front)
TecnologíaSpring Boot 4 · Java 17 · MySQLAstro con renderizado en servidor · Node
Puerto interno80854321
Qué se empaquetaEl .jar compiladoLa carpeta dist/ de la build
ConfiguraciónUsuario y contraseña de la base de datos (DB_USERNAME, DB_PASSWORD)URL de la API (API_URL)
Los secretos no van dentro de la imagen Cualquiera que pueda descargar una imagen puede leer lo que lleva dentro. Por eso el usuario y la contraseña de la base de datos no se escriben en el application.yaml: se leen de variables de entorno (${DB_USERNAME} y ${DB_PASSWORD}), que se pasan al arrancar el contenedor desde un fichero .env que solo existe en la máquina virtual. 
spring:
  datasource:
    url: jdbc:mysql://TU_SERVIDOR.mysql.database.azure.com/pokemondb?useSSL=true&createDatabaseIfNotExist=true
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

4Práctica 1: preparar las imágenes (en tu ordenador)

Las imágenes se construyen en tu ordenador, no en la máquina virtual. Primero se prepara una carpeta de despliegue con lo que lleva cada imagen.

1

La carpeta de despliegue

pokeapi-deploy/
├── back/
│   ├── Dockerfile
│   └── pokeAPI-0.0.1-SNAPSHOT.jar      ← el .jar compilado
└── front/
    ├── Dockerfile
    ├── package.json
    ├── package-lock.json
    └── dist/                            ← la build de Astro

Los dos Dockerfile están en la carpeta ficheros-azure/ de este tema.

2

Compilar el .jar de la API y copiarlo

cd pokeAPI
./mvnw clean package -DskipTests
cp target/pokeAPI-0.0.1-SNAPSHOT.jar ../pokeapi-deploy/back/
3

Compilar el front y copiar la build

cd pokeAPI-front
npm install
npm run build
cp -R dist ../pokeapi-deploy/front/
cp package.json package-lock.json ../pokeapi-deploy/front/

npm run build genera la carpeta dist/ (con client/ y server/). No se copia node_modules: se instala dentro de la imagen, ya preparado para Linux.

4

Los dos Dockerfile

back/Dockerfile: igual que el del Tema 5, con el puerto de esta API.

FROM eclipse-temurin:17-jre

WORKDIR /app
COPY pokeAPI-0.0.1-SNAPSHOT.jar app.jar

EXPOSE 8085

ENTRYPOINT ["java", "-jar", "app.jar"]

front/Dockerfile: ejecuta la build de Astro con Node.

FROM node:22-alpine

WORKDIR /app
ENV NODE_ENV=production \
    HOST=0.0.0.0 \
    PORT=4321

COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY dist ./dist

EXPOSE 4321
CMD ["node", "./dist/server/entry.mjs"]
InstrucciónQué hace
ENVVariables de entorno que la imagen lleva siempre. HOST=0.0.0.0 es obligatorio en un contenedor: sin él el servidor solo escucha dentro de sí mismo y no se puede acceder desde fuera
RUNEjecuta un comando al construir la imagen (aquí, instalar las dependencias de producción)
CMDComando que se ejecuta al arrancar el contenedor (parecido a ENTRYPOINT)
Por qué se copia package.json antes que dist Docker guarda en caché cada instrucción. Si package.json no cambia, el npm ci (lo más lento) no se repite; si solo cambia el código, solo se rehace la copia de dist.

5Práctica 2: Azure Container Registry

Un registro es un almacén de imágenes. Aquí creamos el nuestro en Azure, nos identificamos desde Docker y subimos las dos imágenes.

1

Crear el registro

En el portal de Azure: Registros de contenedor → Crear.

  • Grupo de recursos: el mismo donde estarán la máquina virtual y la base de datos.
  • Nombre: único en todo Azure, en minúsculas y sin guiones (por ejemplo miregistro). Su dirección será miregistro.azurecr.io.
  • SKU: Basic.
2

Activar el usuario administrador

En el registro: Configuración → Claves de acceso → Usuario administrador (activarlo). Aparecen el nombre de usuario y dos contraseñas: son las credenciales con las que Docker se identificará.

3

Iniciar sesión desde Docker

docker login miregistro.azurecr.io

Pide el usuario y la contraseña de las claves de acceso. Debe responder Login Succeeded.

4

Construir las imágenes con el nombre del registro

cd pokeapi-deploy
docker build -t miregistro.azurecr.io/pokeapi-back:1.0  ./back
docker build -t miregistro.azurecr.io/pokeapi-front:1.0 ./front
docker images

El nombre lleva delante la dirección del registro: así Docker sabe a dónde subir cada imagen.

Arquitectura (solo si tu ordenador es un Mac con chip M1, M2, M3…) Las máquinas virtuales de Azure usan procesadores amd64. Si construyes en un Mac con chip Apple, añade --platform linux/amd64 al docker build; si no, la imagen se descargará pero no arrancará (exec format error). Se comprueba con docker image inspect miregistro.azurecr.io/pokeapi-back:1.0 --format '{{.Architecture}}': debe decir amd64.
5

Subir las imágenes

docker push miregistro.azurecr.io/pokeapi-back:1.0
docker push miregistro.azurecr.io/pokeapi-front:1.0

Se comprueba en el portal, en el registro: Servicios → Repositorios. Deben aparecer pokeapi-back y pokeapi-front con la etiqueta 1.0.

6Práctica 3: la máquina virtual

La máquina virtual es el servidor donde se ejecutarán los contenedores. Solo necesita Docker: no lleva ni Java, ni Maven, ni código fuente.

1

Crear la máquina

En el portal: Máquinas virtuales → Crear.

  • Imagen: Ubuntu Server 24.04 LTS.
  • Tamaño: con 2 GB de RAM como mínimo (por ejemplo B1ms). Con 1 GB, Spring Boot y Docker se quedan sin memoria.
  • Autenticación: clave pública SSH. Al terminar, Azure descarga un fichero .pem: es la llave de entrada, hay que guardarla bien.
  • Puertos de entrada: marcar SSH (22) y HTTP (80).
Fijar la IP pública Por defecto la IP es dinámica y cambia cuando se detiene y se vuelve a iniciar la máquina. Para fijarla: IP pública → Configuración → Asignación: Estática. Si cambia, hay que actualizar también la regla de firewall del MySQL.
2

Entrar por SSH

chmod 400 /ruta/a/clave.pem
ssh -i /ruta/a/clave.pem azureuser@IP_DE_LA_MAQUINA

Sin el chmod 400, SSH rechaza la llave con UNPROTECTED PRIVATE KEY FILE: el fichero no puede ser legible para otros usuarios.

3

Instalar Docker y Compose

sudo apt update
sudo apt install -y docker.io docker-compose-v2
sudo usermod -aG docker $USER

Hay que cerrar la sesión SSH y volver a entrar para poder usar docker sin sudo. Se comprueba:

docker --version
docker compose version
docker run hello-world
docker-compose frente a docker compose El paquete docker-compose de apt instala la versión 1 (comando con guion), ya obsoleta, que además falla con versiones recientes de Docker (KeyError: 'ContainerConfig'). El paquete docker-compose-v2 instala la actual, que se usa sin guion: docker compose. Si ya tienes la antigua, funciona igual, pero hay que escribir sudo docker-compose ....
4

Crear un espacio de intercambio (swap)

Es muy recomendable en máquinas con poca memoria: si se agota la RAM, el sistema se bloquea y deja de responder, incluso por SSH.

sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h

free -h debe mostrar 2 GB en la fila Swap.

7Práctica 4: docker-compose en la máquina

Con las imágenes en el registro y Docker instalado, solo falta decirle a la máquina qué contenedores arrancar. Eso lo hace el docker-compose.yml.

1

Permitir la conexión a la base de datos

La base de datos de Azure tiene su propio firewall y, por defecto, no deja entrar a nadie. En el servidor MySQL: Redes → Reglas de firewall → añadir la IP pública de la máquina virtual.

Sin esta regla, la API no arranca y el log muestra Communications link failure.

2

Los dos ficheros de la máquina

En la máquina solo hacen falta dos ficheros en una misma carpeta; las imágenes se descargan del registro.

mkdir ~/pokeapi && cd ~/pokeapi

docker-compose.yml (se sube con scp o se crea con nano):

services:

  backend:
    image: ${REGISTRY}/pokeapi-back:1.0
    container_name: pokeapi-back
    restart: unless-stopped
    environment:
      DB_USERNAME: ${DB_USERNAME}
      DB_PASSWORD: ${DB_PASSWORD}

  frontend:
    image: ${REGISTRY}/pokeapi-front:1.0
    container_name: pokeapi-front
    restart: unless-stopped
    depends_on:
      - backend
    environment:
      API_URL: http://backend:8085/api/v1
    ports:
      - "80:4321"

Para subirlo desde tu ordenador:

scp -i /ruta/a/clave.pem docker-compose.yml azureuser@IP_DE_LA_MAQUINA:~/pokeapi/

.env, que se crea en la máquina:

nano .env
chmod 600 .env
REGISTRY=miregistro.azurecr.io
DB_USERNAME=usuario_de_mysql
DB_PASSWORD=contraseña_de_mysql

El fichero debe llamarse exactamente .env (con el punto), estar en la misma carpeta que el docker-compose.yml y no llevar espacios alrededor del =.

ClaveQué hace
imageEn lugar de build, se descarga una imagen ya hecha del registro. ${REGISTRY} se rellena con el valor del .env
environmentVariables de entorno del contenedor. La API recibe aquí el usuario y la contraseña de la base de datos; el front recibe la URL de la API
API_URLbackend es el nombre del servicio de arriba: Docker lo resuelve solo dentro de su red
ports: "80:4321"Publica el puerto: el 80 de la máquina va al 4321 del contenedor del front. La API no publica ningún puerto
depends_onEl front arranca después de la API
restartunless-stopped: si el contenedor se cae, Docker lo reinicia solo (salvo que lo pares tú)
3

Iniciar sesión en el registro, descargar y arrancar

docker login miregistro.azurecr.io
docker compose config | grep image
docker compose pull
docker compose up -d
docker compose ps
docker compose logs -f backend

docker compose config | grep image comprueba que ${REGISTRY} se ha rellenado: si las imágenes empiezan por /pokeapi..., falta el .env. En el log de la API hay que esperar a Started PokeApiApplication; se sale con Ctrl+C (los contenedores siguen funcionando).

Si la máquina tiene poca RAM Se puede limitar la memoria de Java añadiendo en el servicio backend, dentro de environment, la línea JAVA_TOOL_OPTIONS: "-Xmx300m -XX:+UseSerialGC".
4

Probar

Desde la propia máquina:

curl -I http://localhost

Y desde el navegador de tu ordenador: http://IP_DE_LA_MAQUINA. Deben verse los entrenadores y los Pokémon cargados desde la base de datos de Azure.

Si responde en localhost pero no desde fuera, falta abrir el puerto 80: Redes → Reglas de puerto de entrada → permitir TCP 80.

5

Actualizar la aplicación

Cuando cambia el código no se toca la máquina: se construye y se sube una imagen nueva, y la máquina la descarga. En tu ordenador, con una etiqueta nueva:

docker build -t miregistro.azurecr.io/pokeapi-front:1.1 ./front
docker push miregistro.azurecr.io/pokeapi-front:1.1

En la máquina, se cambia 1.0 por 1.1 en el docker-compose.yml y:

docker compose pull
docker compose up -d

up -d solo recrea los contenedores cuya imagen ha cambiado.

Idea clave de la unidad El flujo de despliegue es siempre el mismo: construir una imagen → subirla a un registro → descargarla en el servidor → arrancarla con Compose. El servidor no necesita el código ni compiladores: solo Docker, el docker-compose.yml y las variables de entorno con los secretos, que nunca van dentro de la imagen.
